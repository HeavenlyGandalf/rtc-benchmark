# A6: прерывание публикации

Проверялось одно свойство: оборванная публикация не должна оставлять сайт в
нерабочем или наполовину обновлённом состоянии.

## Helios — обрыв посреди передачи файлов

Обычную публикацию прервать посреди выгрузки невозможно: 1,8 МБ по SSH
уходят примерно за 4 секунды, а отмена запуска доходит до раннера позже.
Поэтому проверка сделана с одноразовой веткой `test/interruption-throttle`
(удалена после проверки, в `main` не попала): rsync с `--bwlimit=4`, а ветка
публикуется как релиз, а не как превью.

| | |
|---|---|
| запуск | `36696819334`, событие push, ветка `test/interruption-throttle` |
| отменён на шаге | 9 «Выгрузить на Helios», состояние `in_progress` |
| шаг 9 после отмены | `completed/cancelled` — передача оборвана |
| шаг 11 «Переключить публикацию» | `skipped` — указатель не переключён |
| итог запуска | `cancelled` |
| production до | `785edb07b6747eec2f61410200b00274fd01a164` |
| production после | `785edb07b6747eec2f61410200b00274fd01a164`, HTTP 200 |
| на сервере после | частичный каталог `3d560737…` (49 файлов из 63) лежит рядом с полными, `current` на него не указывает |

Частичный каталог в итоге отсутствует (в снятой после проверки раскладке его
нет), удалён был вручную: запуск отменили, поэтому следующие шаги, включая
уборщик релизов, не выполнялись. Уборщик и не тронул бы его: маркер
`.rtc-benchmark` в нём есть, а он появляется на этапе подготовки каталога
приёмника, до начала передачи.

Это и есть разница со старой схемой: там файлы писались прямо в рабочий
каталог, и обрыв на середине оставлял сайт без части файлов.

## GitHub Pages — два окна

| запуск | отменён на шаге | что вышло | сайт после |
|---|---|---|---|
| `36698690038` | 3 «Опубликовать в GitHub Pages» | шаг всё равно завершился `success` за 8 с, проверка публикации `skipped`, запуск `cancelled` | 200 |
| `36698825693` | 4 «Установить зависимости» | сборка доехала целиком, job публикации не запустилась вовсе, запуск `cancelled` | 200 |

Наблюдение: отмена запуска не обязана прерывать уже идущий шаг — она мешает
начать следующие. На Helios сработало иначе, потому что `rsync` с
`--bwlimit=4` шёл с 09:33:35 до 09:49:53, то есть 16 минут 18 секунд, и
успел получить сигнал. Оценка «около половины минуты», которая стояла в
комментарии тестовой ветки, оказалась занижена на порядок — по факту
выгрузка шла в тридцать раз дольше. На Pages оба прерванных шага короче
десяти секунд.

Отсюда практический вывод для Pages: окно, в котором прерванная публикация
может навредить, — только между началом `deploy-pages` и его завершением, и
оно узкое. Проверка публикации добавлена именно на другую сторону окна:
убедиться, что публикация вообще состоялась.
