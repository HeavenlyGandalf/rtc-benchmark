# Эксперимент: замеры с эмуляцией сети

Инфраструктура Этапа 1 (см. [`docs/experiment-plan.md`](../docs/experiment-plan.md)):
воспроизводимый прогон сценариев 1–3 для WebRTC и WebTransport под
контролируемыми сетевыми профилями.

## Состав

| Файл | Назначение |
|---|---|
| `profiles.json` | сетевые профили (задержка/джиттер/потери/полоса) |
| `netem.mjs` | применение/снятие профиля через `tc netem` (нужен NET_ADMIN) |
| `../scripts/run-series.mjs` | один прогон серии (4 канала × сценарии 1–3), сырые числа → `results/raw/*.json` |
| `../scripts/aggregate.mjs` | сводка по прогонам → `results/summary.csv` + `summary.json` |
| `Dockerfile`, `compose.yml`, `run-all.sh` | Linux-стенд + headless Chromium + оркестрация всех профилей |

## Основной способ: план эксперимента и `make`

Целевая топология — `compose-router.yml`: клиент (`bench`), контейнер-маршрутизатор
с `tc netem` (`router`) и стенд (`server`) в разных сетях. Эмуляция сети не стоит
на конечных узлах, поэтому не искажает поведение транспорта.

Пошаговая инструкция для проверяющего — раздел 0 корневого [`README.md`](../README.md).

```bash
make image          # собрать образ (за прокси: BUILD_ARGS="--build-arg HTTPS_PROXY=...")
make smoke          # дымовая проверка: сервисы, объект исследования, netem, метрики, манифест (~2 мин)
make verify         # калибровка → 40 прогонов по experiment/plan-verify.json → анализ → сверка с results/reference
make experiment     # полный план experiment/plan.json (300 прогонов, ~14 ч) → анализ → графики
make analyze NAME=verify   # анализ и графики по сохранённым сырым данным
```

| Файл | Назначение |
|---|---|
| `plan.json`, `plan-verify.json`, `plan-smoke.json` | факторы, уровни, число прогонов, A/A-партия, сид, параметры серии |
| `../scripts/run-plan.mjs` | калибровка, рандомизированное расписание, прогрев, прогоны, повтор упавших |
| `../scripts/calibrate.mjs` | UDP-эхо под каждым профилем: RTT ≈ 2·delay ± 2 мс, потери ≈ 1 − (1 − p)² |
| `../scripts/analyze.mjs` | единица анализа — прогон; бутстреп-ДИ, Манн–Уитни, Холм, A/A, тренд по номеру прогона → `analysis.md` |
| `../scripts/plots.mjs` | SVG-графики серии: ящики с точками прогонов, ECDF RTT, стабильность, A/A → `plots/` |
| `../scripts/smoke.mjs`, `smoke-entry.sh` | дымовая проверка стенда (`make smoke`) |
| `../scripts/compare.mjs` | сверка с эталоном, PASS/FAIL и код выхода |
| `netem-agent.mjs` | HTTP-управление netem в контейнере-маршрутизаторе |
| `architecture.mmd` | диаграмма стенда (Mermaid) |

Каждый прогон пишет в `results/<план>/raw/<run-id>.json` сырые выборки и
манифест: коммит, digest образа, версию Chromium, ядро, лимиты CPU и памяти,
профиль, сид, порядок каналов, CPU клиента и сервера и задержку event loop
по окнам сценариев.

## Пилотный запуск (Docker, netem на `lo`)

```bash
docker compose -f experiment/compose.yml run --rm bench
```

Прогонит все профили из `compose.yml` (`PROFILES`), на каждом применит netem,
соберёт сырые данные и выполнит агрегацию. Результаты — в `./results/`
(`raw/*.json`, `summary.csv`, `summary.json`).

Сузить набор профилей или параметры:

```bash
PROFILES="lan lossy" REPS=30 docker compose -f experiment/compose.yml run --rm -e PROFILES -e REPS bench
```

## Профили

| Профиль | Задержка | Потери | Полоса |
|---|---|---|---|
| `lan` | 0 (базовая линия) | 0% | — |
| `wifi` | 15 мс ± 5 | 0.5% | — |
| `4g` | 50 мс ± 15 | 1% | — |
| `5g` | 25 мс ± 8 | 0.2% | — |
| `lossy` | 40 мс | 5% | — |
| `limited` | 20 мс | 0% | 5 Мбит/с |
| `4g-noreorder` | 50 мс ± 15 | 1% | 1 Гбит/с — только чтобы netem не переупорядочивал пакеты |

Значения — на один проход маршрутизатора; netem стоит на обоих его интерфейсах, поэтому
RTT ≈ 2 × задержки. Калибровка (`calibrate.mjs`) ожидает медиану RTT 2·delay ± 2 мс
(с полосой — плюс сериализация кадра), потери 1 − (1 − p)²; для `4g-noreorder` — медиану
в [2·delay; 2·(delay + jitter)] и не больше 0,5 % переупорядоченных пакетов: с `rate`
пакет ждёт предыдущий, и джиттер превращается в очередь.

**Оговорка про `4g-noreorder`.** Задержка прохода здесь — скользящий максимум
max(dᵢ, Dᵢ₋₁ − Δt), поэтому она зависит от темпа пакетов: при шаге 1 мс (калибровка)
медиана ≈ 59–60 мс на проход, при шаге сообщений стенда 10 мс — около 52 мс; надёжные
каналы (дополнительные ACK) и сценарий пропускной способности видят ещё большую
задержку. Значит, разница `4g` и `4g-noreorder` — это не «только переупорядочивание»,
а переупорядочивание плюс зависящая от трафика добавка к задержке. Сравнивать профили
нужно по измеренным медианам RTT ненадёжных каналов, а не по номинальным 50 ± 15 мс.

**Методика пилота** (`compose.yml`): netem задаётся на `lo`, через который проходят и запрос, и эхо,
поэтому измеренный RTT ≈ 2 × односторонней задержки профиля. Сравниваются
относительные величины WebRTC vs WebTransport при одинаковом профиле.

## Локальный прогон без эмуляции (быстрая проверка)

На хосте (сеть не эмулируется, профиль помечается как `none`):

```bash
yarn start          # в одном терминале
yarn series         # в другом: один прогон → results/raw/none-*.json
yarn aggregate      # сводка → results/summary.csv
```
