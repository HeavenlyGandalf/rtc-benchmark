## A. Автоматизация публикации и её проверки

### A1–A2. Раскладка релизов на Helios

Сайт не выгружается поверх себя: каждый релиз живёт в своём каталоге, а
`current` — символьная ссылка на живой.

```
~/public_html/
├── rtc-benchmark                    -> rtc-benchmark-releases/<sha>
├── rtc-benchmark-releases/
│   ├── <sha>/                       неизменяемый каталог релиза
│   ├── current -> <sha>             какой релиз жив сейчас
│   ├── .previous                    sha предыдущего, для ручного отката
│   ├── .rtc-benchmark               каталог для rsync, переименовывается
│   ├── preview/                     черновик
│   └── legacy-20260930T074053Z/     сайт, задевший до перехода на схему
├── .rtc-benchmark                   символьная ссылка на живой релиз
└── .legacy
```

Фактическое состояние проверено по SSH после последнего развёртывания:

```text
current -> 3658a9fcbb08a1d222353084161333e46244c9fd
.previous: 785edb07b6747eec2f61410200b00274fd01a164
каталогов релизов: 5
```

Пять каталогов — это `HELIOS_KEEP_RELEASES` по умолчанию. `legacy-` в счёт не
входит: он создан миграцией и не является обычным релизом.

### A4. Проверка публикации на GitHub Pages

Workflow принимает параметр `healthcheck_marker`. Ожидаемый маркер берётся из
сборки; если сайт опубликовался, но маркера нет, публикация считается неудачной.

Проверка делает три вещи: открывает главную, ищет маркер в её HTML, открывает
`search/search_index.json`. Десять попыток с интервалом 10 секунд — сайт
показывает задержку распространения.

| Запуск | Сценарий | Результат |
| --- | --- | --- |
| `36690988716` | обычный запуск `main` | build, deploy, verify — `success` |
| `36691288086` | вручную, заведомо неверный маркер | build и deploy — `success`, **verify — `failure`** через 10 попыток |

Точный вывод шага проверки в неудачном запуске:

```text
::error::Публикация на GitHub Pages не подтверждена: маркер «<marker>» не найден на https://heavenlygandalf.github.io/rtc-benchmark/ за 10 попыток
```

Откатить публикацию на Pages нельзя — в отличие от Helios, там нет смены
символьной ссылки. Запуск честно падает, а сайт остаётся доступным: это
и проверено, после неудачного запуска главная отдавала 200.

## D. Ошибки сборки и их устранение

Три ошибки воспроизведены на копии проекта; менялся только `mkdocs.yml`.
Полный вывод — в [`evidence/d13-debug-repro.log`](evidence/d13-debug-repro.log).

### D1. Неизвестная опция `base_url`

В MkDocs 1.6 нет опции верхнего уровня `base_url`: она существует только у
отдельных плагинов. Базовый путь выводится из `site_url`.

Добавлено рядом с `site_url`:

```yaml
base_url: "/rtc-benchmark/"
```

Команда `python -m mkdocs build --strict`, точный вывод:

```text
WARNING -  Config value 'base_url': Unrecognised configuration name: base_url
Aborted with 1 configuration warnings in 'strict' mode!
```

Устранение: задать `site_url` целиком, отдельное поле не нужно.

```yaml
site_url: "https://heavenlygandalf.github.io/rtc-benchmark/"
```

### D2. `sitemap.xml` собирается пустым

При незаданном `site_url` файл создаётся, но пуст — это проверяемый признак
неверной настройки базового адреса, а не пустая сборка.

| | URL в `sitemap.xml` | размер | канонических ссылок |
| --- | --- | --- | --- |
| без `site_url` | 0 | 109 байт | 0 |
| с `site_url` | 11 | — | 1 |

Первый адрес в исправленной сборке:

```text
<loc>https://heavenlygandalf.github.io/rtc-benchmark/</loc>
```

### D3. Ссылку нельзя поставить в `copyright`

Значение `copyright` подставляется в шаблон как есть: markdown не
обрабатывается, относительные пути не переписываются.

```yaml
copyright: "[CC BY 4.0](license.md)"
```

В подвале главной получается:

```html
<div class="md-copyright__highlight">
  [CC BY 4.0](license.md)
</div>
```

То есть текст с разметкой вместо ссылки: тега `<a href="license.md">` на
странице нет, и цели по этому пути не существует — в сборке есть только каталог
`site/license/`. Ссылка битая.

Устранение: в `copyright` оставить только текст, разбор лицензий вынести на
отдельную страницу, добавленную в `nav`.

### E2. Сравнение генераторов статических сайтов

Один и тот же проект — 15 страниц с русскими заголовками, front matter,
таблицей и формулой — собран четырьмя генераторами. Для каждого: 6 сборок подряд,
первая отбрасывается как прогрев, в таблицу идут 5. Перед каждым запуском
выходной каталог удаляется целиком.

| Генератор | мин | медиана | макс | размер | html | файлов |
| --- | --- | --- | --- | --- | --- | --- |
| MkDocs 1.6.1 + Material 9.7.7 | 0.36 с | 0.36 с | 0.36 с | 4.77 МБ | 16 | 64 |
| Sphinx 9.1.0 + MyST 5.1.0 | 0.59 с | 0.60 с | 0.61 с | 0.49 МБ | 18 | 69 |
| Pelican 4.12.0 | 0.26 с | 0.27 с | 0.27 с | 0.62 МБ | 22 | 40 |
| Quarto 1.8.24 | 4.20 с | 4.27 с | 4.32 с | 1.45 МБ | 16 | 34 |

Скорость сборки ограничением не была: любой из четырёх укладывается в секунды,
и все быстрее самой публикации на Helios (23–32 с из A5). Quarto медленнее
остальных примерно в 7–16 раз, но 4.3 с на 15 страниц — не проблема.

Размер MkDocs — 4.77 МБ из-за вендоренного MathJax (2.1 МБ). Без него сайт
весит 2.76 МБ, но формулы не отрисовываются вовсе. Sphinx здесь меньше только
потому, что тянет MathJax из CDN.

Число html-файлов не равно числу страниц: у Pelican 22 файла, потому что он по
умолчанию добавляет архивы, авторов, категории и теги; у MkDocs 16 — 15
страниц плюс 404; у Sphinx 18 — плюс `genindex` и `search`.

**Формулы, проверено в браузере:**

| Генератор | Результат | Чем рисует |
| --- | --- | --- |
| MkDocs | отрисована | локальный MathJax, SVG |
| Sphinx | отрисована | MathJax 4 из CDN, CHTML |
| Pelican | осталась текстом | поддержки нет |
| Quarto | отрисована | MathJax из CDN, CHTML |

Признак отрисованной формулы — контейнер `mjx-container`, а не `svg` внутри
него: в режиме CHTML (так настроены Sphinx и Quarto) MathJax строит HTML, и
svg там нет. Первая версия проверки искала только svg и объявляла CHTML-формулы
неотрисованными — ложный отрицательный результат, который едва не попал в
отчёт.

**Что стоит знать про настройку.** Три находки, каждая стоила отдельного
захода. Все три дают тихо неправильную документацию: сборка проходит, ошибок
нет.

1. **MyST не понимает `toctree` без явного указания.** Ни `.. toctree::`, ни
   `:::{toctree}` не разрешились: директива попала в HTML как обычный текст,
   сборка завершилась с 15 предупреждениями `document isn't included in any
   toctree`, оглавление не работало. Сработала огороженная форма
   ` ```{toctree} `. Исходники не попадали в оглавление — случай, где нужен
   `-W`, а не `-q`.
2. **`$$...$$` в MyST не включён по умолчанию.** Без
   `myst_enable_extensions = ["dollarmath"]` формула становится обычным
   текстом, и Sphinx не говорит ни слова.
3. **Математика в MkDocs требует подключения отрисовщика.** Настройки
   `pymdownx.arithmatex` достаточно, чтобы появилась разметка, но без
   `extra_javascript` в собранном сайте нечем рисовать формулу.

Про Pelican отдельно: имя файла страницы он строит из заголовка и
транслитерирует кириллицу, поэтому `«Команды»` превращается в `komandy.html`.

**Вывод.** Выбран MkDocs: он уже используется в проекте, и единственный рисует
формулы локально, без зависимости от внешней сети — для документации, которую
читают в закрытом контуре, это решающий довод. Sphinx и Quarto формулы рисуют,
но тянут MathJax из CDN; Pelican формулы не поддерживает вовсе.

### E3. Что осталось непроверенным

- Вёрстка и формулы в браузерах, кроме Chrome: Safari и Firefox не
  проверялись.
- Мобильная вёрстка: сайт смотрели только на широком экране.
- A5 — не A/B-тест на одном коммите, старых запусков всего 3 (см. A5).
- Чистое сравнение схем публикации на идентичном состоянии репозитория не
  проводилось.
