# WebRTC

В стенде WebRTC используется для двух задач: передачи данных через каналы
SCTP (сценарии 1–3) и видеотрансляции через встроенный медиастек браузера
(сценарий 4).

Реализация клиента — `src/client/transports/webrtc.ts` и
`src/client/video/webrtcVideo.ts`, сервера — `src/server/webrtc.ts`.

## Соединение

```ts
const pc = new RTCPeerConnection({ iceServers: [] });
const reliableDc = pc.createDataChannel('reliable');
const unreliableDc = pc.createDataChannel('unreliable', { ordered: false, maxRetransmits: 0 });
```

`iceServers` пуст: ни STUN, ни TURN не используются, соединение строится только
по локальным кандидатам. Сертификат DTLS самоподписанный и сверяется браузером с
отпечатком `a=fingerprint` из SDP-ответа — цепочка CA не проверяется.

Оба канала создаются сразу при подключении, и `binaryType` переключается в
`arraybuffer` — измеряемые сообщения бинарные.

## Сигналинг без trickle ICE

```text
клиент                                      сервер
  createOffer + setLocalDescription
  ждём iceGatheringState === complete
  POST /api/webrtc/offer { sdp } ---------->  setRemoteDescription
  <---------- answer (полный SDP)             ждём own gathering complete
  setRemoteDescription(answer)
  ждём open обоих каналов
```

Trickle ICE не используется: браузер сначала собирает все кандидаты и только
потом отправляет offer, сервер отвечает после завершения собственного сбора
кандидатов. Поэтому в измеренное время установления соединения входит ожидание
окончания сбора кандидатов с обеих сторон — это заметно увеличивает время
установления по сравнению с WebTransport.

Сервер (`node-datachannel`) отвечает по событию `onGatheringStateChange` со
значением `complete`; на случай, если кандидаты не соберутся, установлен
таймаут 10 секунд, после которого соединение закрывается, а запрос отклоняется
ошибкой `ICE gathering timeout`.

## Каналы данных

| Канал | Режим | Особенности |
|---|---|---|
| `reliable` | надёжный, упорядоченный | по умолчанию, SCTP с подтверждениями |
| `unreliable` | `ordered: false`, `maxRetransmits: 0` | потери допустимы, доставка без повторов |

Предельный размер одного сообщения берётся из `sctp.maxMessageSize`, который
согласован в SDP (при отсутствии значения используется 65536 байт). Заданный в
сценарии размер, превышающий лимит, уменьшается автоматически; лимиты всех
каналов собраны в [Методике](methodology.md#message-size).

Обратное давление: при `bufferedAmount > 1 МБ` отправка ждёт события
`bufferedamountlow` (порог установлен в 512 КБ), поэтому поток не может
переполнить буфер SCTP. Сводка по всем каналам — в
[Методике](methodology.md#backpressure).

## Видеотрансляция (сценарий 4)

```text
getUserMedia (640×480, 30 fps)
  → pc.addTrack
  → RTP/SRTP → эхо-сервер → те же RTP-пакеты обратно
  → pc.ontrack → <video>
```

Кодек согласуется через SDP, шифрование — SRTP, скорость передачи
адаптируется встроенным в браузер механизмом GCC. Сервер на входящий медиатрек
назначает `RtcpReceivingSession` и отправляет каждый полученный RTP-пакет
обратно.

Метрики берутся из `pc.getStats()` раз в секунду:

| Метрика | Источник |
|---|---|
| кадров/с | `inbound-rtp` (video): `framesPerSecond` |
| разброс задержки | `inbound-rtp`: `jitter · 1000` |
| потери пакетов | `inbound-rtp`: `packetsLost` |
| скорость приёма | прирост `bytesReceived` между отсчётами |
| RTT | номинированная `candidate-pair`: `currentRoundTripTime · 1000` |
| сквозная задержка | `requestVideoFrameCallback`: `expectedDisplayTime − captureTime` |

!!! warning "Сквозная задержка обычно недоступна"
    Временные метки захвата камеры не переносятся через стек WebRTC, и
    `VideoFrameCallbackMetadata.captureTime` приходит пустым, поэтому в таблице
    будет `—`. Для сравнения сквозной задержки используется видеосценарий
    WebTransport, где метрика считается от выхода кадра из энкодера до
    отрисовки на `canvas`.

## Отличия от WebTransport, важные для сравнения

- Время установления соединения включает согласование SDP и полный сбор
  кандидатов ICE, а не только криптографическое рукопожатие.
- Ненадёжный канал — это SCTP без повторной передачи, а не дейтаграммы QUIC:
  работает выше стека SCTP со своей логикой перегрузки.
- Медиастек готов в браузере, приложение не кодирует и не декодирует видео само.
- Отпечаток сертификата приходит по SDP неявно, в отличие от WebTransport, где
  клиент обязан передать его явно через `serverCertificateHashes`.
