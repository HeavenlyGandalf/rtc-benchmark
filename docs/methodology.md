# Методика эксперимента

## Общий принцип

Все измерения выполняются **одним и тем же кодом на стороне клиента** поверх
единого интерфейса `BenchChannel` (`src/client/transports/types.ts`):

```ts
export interface BenchChannel {
  mode: ChannelMode;
  /** Максимальный размер сообщения, байт (0 — без практического лимита) */
  maxMessageSize: number;
  send(data: Uint8Array): Promise<void>;
  onMessage(cb: (data: Uint8Array) => void): void;
  close(): Promise<void>;
}
```

Четыре реализации — надёжный поток WebTransport, дейтаграммы WebTransport,
надёжный и ненадёжный каналы данных WebRTC — отличаются только способом
отправки и приёма. Сценарии измерений (`src/client/bench.ts`) не знают, каким
транспортом реализован канал, поэтому разница в результатах отражает свойства
транспорта, а не разницу в коде измерения.

## Эхо-семантика

Оба сервера возвращают клиенту ровно то, что получили, ничего не анализируя и
не изменяя:

- WebTransport: надёжные потоки — `stream.readable.pipeTo(stream.writable)`
  (байт-в-байт), дейтаграммы — эхо каждой полученной дейтаграммы;
- WebRTC: сообщения DataChannel возвращаются как есть, RTP-пакеты медиатреков
  отправляются обратно отправителю.

Из-за этого любое измеряемое значение отражает **клиент, канал и сервер
одновременно**, а сценарии 1–3 дают сопоставимые между собой числа.

Сигналинг WebRTC — единственный неэхо-обмен: браузер отправляет
`POST /api/webrtc/offer` с SDP, сервер отвечает SDP-ответом. Хеш сертификата
для WebTransport клиент получает из `GET /api/info`.

## Формат измеряемых сообщений

```text
[uint32 seq][float64 sendTime][padding до заданного размера]
```

Заголовок — 12 байт (`MSG_HEADER` в `src/client/util.ts`). Номер сообщения
позволяет сопоставить отправку с эхом; остальное — заполнитель нужного размера.
Оба эхо-сервера работают со всеми каналами одинаково, поэтому форма сообщения не
влияет на результат.

## Что входит в измерение

- Сценарии 1–3 измеряются в браузере через `performance.now()`; сервер в этих
  измерениях не участвует, он только эхо. Метрики видеосценария WebRTC приходят
  из `pc.getStats()` и считаются браузером по OwnRTCStatsReport.
- Отправитель и получатель находятся на одном хосте, поэтому используется один
  и тот же источник времени.
- Один прогон = один канал; четыре канала сравниваются последовательно в одном
  запуске сценария.
- Перед основной серией сообщений в сценарии 2 выполняется **прогрев**
  (`warmup`), который в статистику не входит.
- После отправки серии даётся фиксированное время ожидания хвоста эха: 500 мс в
  сценарии 2 и 700 мс дренажа очередей в сценарии 3.
- Между повторами сценария 1 делается пауза 100 мс.

## Обратное давление {#backpressure}

Скорость отправки ограничивается не таймером, а готовностью канала принять
данные, поэтому измеряется реальная пропускная способность, а не скорость
генерации сообщений:

| Канал | Механизм |
|---|---|
| WT надёжный поток | `await writer.ready` и `await writer.write` (flow control QUIC) |
| WT дейтаграммы | `await writer.ready` / `write`; доставка при этом ненадёжная |
| WebRTC DataChannel | при `bufferedAmount > 1 МБ` отправка ждёт события `bufferedamountlow` (порог 512 КБ) |

## Ограничения размера сообщения {#message-size}

Размер сообщения автоматически ограничивается возможностями канала:

| Канал | `maxMessageSize` |
|---|---|
| WT надёжный поток | `0` — практического лимита нет |
| WT дейтаграммы | `datagrams.maxDatagramSize`, иначе 1200 байт |
| WebRTC DataChannel | `sctp.maxMessageSize` из SDP, иначе 65536 байт |

!!! warning "Эффективный размер не показывается в результатах"
    Если заданный размер больше лимита канала, он уменьшается автоматически, но
    в колонку «Параметры» таблицы результатов и в CSV попадает **запрошенный**
    размер, а не фактический. Поэтому строку с метриками ненадёжного канала
    нельзя читать как «сообщения по 16384 Б»: фактически отправлялось по 1200 Б
    (WebTransport) или по `sctp.maxMessageSize` (WebRTC). Сверяйтесь с таблицей
    выше.

## Определения метрик {#metric-definitions}

Метрики RTT вычисляются в `computeRttStats` (`src/client/util.ts`):

| Метрика | Определение |
|---|---|
| среднее | арифметическое среднее по полученным RTT |
| медиана | элемент отсортированного ряда с индексом `floor(n / 2)` |
| p95, p99 | элемент ряда с индексом `min(n - 1, floor(p / 100 · n))` — ближайший ранг |
| σ | `sqrt(Σ (RTT − среднее)² / n)` |
| джиттер | сглаженное среднее отклонение между соседними RTT по RFC 3550: `j += (|RTTᵢ − RTTᵢ₋₁| − j) / 16` |
| потери | `(отправлено − получено) / отправлено · 100 %` |
| скорость приёма эха | `байты_эха · 8 / 10⁶ / (длительность_отправки / 1000)`, Мбит/с |

Для сценария 1 считаются только среднее и медиана времени установления
соединения. Длительность фазы отправки в сценарии 3 — от первого сообщения до
последнего; окно дренажа в неё не входит, но в него попадает вернувшийся хвост
эха.

### Формулы {#formulas}

Те же определения в записи TeX. Формулы рисует MathJax, вложенный в репозиторий
(`docs/assets/mathjax/`): страница не обращается ни к одному внешнему хосту, поэтому
формулы видны и на закрытом хостинге. В исходниках страницы разделители — обычные
`\( \)` и `\[ \]`.

Среднее и стандартное отклонение:

\[
\bar{x} = \frac{1}{n}\sum_{i=1}^{n} x_i,
\qquad
\sigma = \sqrt{\frac{1}{n}\sum_{i=1}^{n}(x_i - \bar{x})^2}
\]

Перцентиль ближайшего ранга: \(x_{(p)}\) — элемент отсортированного ряда с
индексом \(\min(n - 1, \lfloor p n / 100 \rfloor)\). Медиана — это
\(x_{(50)}\), то есть \(\text{median} = x_{(\lfloor n/2 \rfloor)}\).

Джиттер по RFC 3550 — сглаженное среднее отклонение между соседними RTT,
\(j_0 = 0\):

\[
j_i = j_{i-1} + \frac{|x_i - x_{i-1}| - j_{i-1}}{16}
\]

Доля потерянных сообщений в процентах, где \(N_{\text{отпр}}\) — отправлено,
\(N_{\text{пол}}\) — получено:

\[
L = \frac{N_{\text{отпр}} - N_{\text{пол}}}{N_{\text{отпр}}} \cdot 100\,\%
\]

Скорость приёма эха в Мбит/с, где \(B_{\text{эха}}\) — суммарный размер
возвращённых сообщений в байтах, а \(T_{\text{отпр}}\) — длительность фазы
отправки в миллисекундах:

\[
B = \frac{8\,B_{\text{эха}}}{10^{6}} \big/ \frac{T_{\text{отпр}}}{1000}
\]

Деление на \(10^{6}\) переводит байты в мегабайты, а деление на \(T_{\text{отпр}}/1000\) —
миллисекунды в секунды; вместе это даёт мегабиты в секунду. Проверить
соответствие коду можно по строке
`(receivedBytes * 8) / 1_000_000 / (durationMs / 1000)` в `src/client/bench.ts`.

## Порядок проведения измерений

Рекомендуемая последовательность, чтобы результаты были сравнимы:

1. Запустить стенд и дождаться сообщения `✓ Все необходимые API поддерживаются`.
2. Выполнить сценарий 1 (время установления соединения) — он не держит соединения
   после себя.
3. Выполнить сценарий 2 (RTT) и сценарий 3 (пропускная способность) — каждый
   открывает соединения на время прогона и закрывает их.
4. Сценарий 4 (видео) запускать отдельно от сценариев 1–3: сервер — один поток
   Node, и видеонагрузка конкурирует с измерениями данных.
5. Выгрузить накопленные результаты кнопкой «Экспорт CSV».

Повторные прогоны одного и того же сценария на одном и том же хосте дают
сравнимые между собой числа; смешивать результаты разных машин и разных сетей
нельзя (см. [Ограничения](limitations.md)).

## Чего методика не учитывает

- Задержку вывода на экран: для WebTransport сквозная задержка считается от
  выхода кадра из энкодера до отрисовки на `canvas`.
- В RTT входит и сборка сообщения, и постановка его в канал: отметка времени
  снимается перед `buildMessage` и `send`. Время, потраченное браузером **до**
  постановки сообщения в канал (кодирование видео, работа с UI), в замер не
  входит.
- Влияние сети с потерями: TURN не настроен, `iceServers` пуст, эмуляции
  задержки и перегрузки нет.
