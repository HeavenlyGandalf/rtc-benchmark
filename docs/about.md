# О проекте

## Предмет исследования

Проект — экспериментальный стенд к НИР «Сравнительный анализ технологий WebRTC и
WebTransport для передачи данных в реальном времени в веб-приложениях». Стенд
измеряет обе технологии **на одних и тех же сценариях и через одни и те же
эхо-серверы**, чтобы полученные числа можно было сравнивать между собой.

## Цель эксперимента

Получить сопоставимые количественные характеристики двух транспортов реального
времени в веб-браузере:

- время установления соединения;
- задержка обмена (RTT), её разброс и джиттер;
- потери сообщений на ненадёжных каналах;
- пропускная способность (скорость приёма эха);
- параметры видеотрансляции через сервер: сквозная задержка, частота кадров,
  скорость приёма.

Одновременно стенд показывает, **сколько работы приложение берёт на себя** при
использовании WebTransport: медиастек там строится средствами WebCodecs вручную,
тогда как WebRTC предоставляет его готовым.

## Что сравнивается

| | WebRTC | WebTransport |
|---|---|---|
| Транспортный уровень | UDP + DTLS (ICE) | UDP + QUIC (HTTP/3) |
| Каналы данных | SCTP: надёжный и ненадёжный (`maxRetransmits: 0`) | надёжный поток и дейтаграммы |
| Шифрование | DTLS-SRTP | TLS 1.3 внутри QUIC |
| Медиастек | встроенный в браузер | приложения (WebCodecs) |
| Согласование | SDP offer/answer + сбор ICE-кандидатов | встроено в протокол, сигналинг не нужен |
| Серверная реализация в стенде | `node-datachannel` (libdatachannel) | `@fails-components/webtransport` (quiche) |
| Сертификат | не проверяется (пустой `iceServers`) | самоподписанный, отпечаток передаётся в `serverCertificateHashes` |

## Архитектура стенда

Стенд состоит из трёх частей:

1. **Клиент** — статическая страница на <http://localhost:8080> (TypeScript,
   сборка в `public/app.js` через esbuild). Запускает сценарии, рисует графики
   (chart.js) и выгружает результаты в CSV.
2. **HTTP/1.1 сервер** (порт `HTTP_PORT`, по умолчанию 8080) — отдаёт статику,
   отдаёт метаданные (`GET /api/info`) и обслуживает сигналинг WebRTC
   (`POST /api/webrtc/offer`).
3. **Эхо-серверы** — WebRTC на `node-datachannel` и WebTransport на HTTP/3
   (порт `WT_PORT`, по умолчанию 4433, UDP). Оба возвращают клиенту ровно то,
   что получили: сообщения каналов данных, RTP-пакеты и байты потоков.

```text
браузер (клиент)                      Node.js
┌──────────────────────┐
│ сценарии 1–4         │  HTTP/1.1  ┌──────────────────────────────┐
│ ── WebTransport ─────┼───QUIC────▶│ WebTransport echo (/echo)     │
│ ── WebRTC DC ────────┼───DTLS────▶│ WebRTC echo (node-datachannel)│
└──────────────────────┘  ◀──эхо──  └──────────────────────────────┘
```

Схема передачи данных по каналам:

| Сценарий | Клиент → сервер | Сервер → клиент |
|---|---|---|
| WT надёжный поток | `createBidirectionalStream()`, кадры `[u32 len][payload]` | `pipeTo` того же потока (байт-в-байт) |
| WT дейтаграммы | `wt.datagrams.writable` | эхо входящей дейтаграммы |
| DataChannel надёжный | `createDataChannel('reliable')` | эхо сообщения |
| DataChannel ненадёжный | `createDataChannel('unreliable', {ordered:false, maxRetransmits:0})` | эхо сообщения |
| Видео WebRTC | `addTrack` → RTP по SRTP | те же RTP-пакеты обратно |
| Видео WebTransport | `VideoEncoder` → QUIC-поток, кадр `[u32 len][u8 key][u32 seq][f64 ts][VP8]` | байт-в-байт эхо → `VideoDecoder` |

## Что стенд не делает

- Не измеряет транспорт в реальной сети: клиент и сервер на одном хосте
  (см. [Ограничения](limitations.md)).
- Не использует TURN, не эмулирует задержку, джиттер и потери в сети.
- Не хранит результаты: замеры выгружаются в CSV вручную из интерфейса.
- Не предназначен для публичного доступа — авторизации нет
  (см. раздел «Безопасность» в `README.md`).
