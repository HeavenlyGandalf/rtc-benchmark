# План доработки экспериментальной части

**Тема:** Экспериментальное сравнение WebRTC и WebTransport для передачи данных
в реальном времени в веб-приложениях.

**Статус документа:** черновик плана на согласование. Дата: 2026-11-01.

**Связь с НИР.**
- НИР‑1 (обзор источников, 25.01.2026) — вывод: нужны дальнейшие исследования
  **производительности, надёжности и удобства разработки** WebTransport.
- НИР‑2 (сравнительный анализ, 29.06.2026) — разработаны **12 формализованных
  критериев** и **6 типовых сценариев**; работа теоретическая, в заключении
  прямо указано на необходимость **экспериментального измерения
  производительности WebTransport**.

Эксперимент = стенд `rtc-benchmark`. Его задача — **эмпирически проверить
теоретические утверждения НИР‑2** (в первую очередь количественные критерии и
рекомендации по сценариям), а не вводить новые.

---

## 1. Цель и гипотезы

**Цель.** Получить воспроизводимые количественные данные по WebRTC и
WebTransport на одинаковых сценариях и в контролируемых сетевых условиях и
сопоставить их с теоретическими выводами НИР‑2.

**Проверяемые гипотезы** (сформулированы из утверждений НИР‑2):

| № | Гипотеза из НИР‑2 | Критерий НИР‑2 |
|---|---|---|
| H1 | WebRTC (P2P) даёт меньшую задержку, чем WebTransport (клиент‑сервер), за счёт отсутствия серверного хопа | К1 задержка |
| H2 | WebTransport устанавливает соединение быстрее WebRTC (QUIC 1‑RTT/0‑RTT против ICE+DTLS) | К1/К11 |
| H3 | Ненадёжная доставка (WT datagrams, RTC unreliable) даёт меньшую задержку и её разброс при потерях, чем надёжная | К4/К5 |
| H4 | WebTransport (QUIC‑потоки) не страдает от HoL‑блокировки при потерях, в отличие от надёжного канала поверх упорядоченной доставки | К6 |
| H5 | WebTransport масштабируется по числу клиентов лучше P2P‑WebRTC | К8 |
| H6 | При росте потерь/задержки/джиттера характеристики деградируют согласно ожиданиям по сценариям 1–6 | все |

Качественные критерии НИР‑2 (архитектура, стек, встроенные медиа, безопасность,
поддержка браузерами, зрелость) **экспериментом не измеряются** — они уже
обоснованы теоретически; в отчёте они приводятся как фиксированные факты.

## 4. Методология (ключевая доработка)

Текущий стенд работает **только на loopback** (localhost), поэтому абсолютные
числа RTT (< 1 мс) непригодны для выводов — это зафиксировано в самом README
(раздел «Ограничения»). Главная доработка — **контролируемые сетевые условия**
и **статистическая строгость**.

### 4.1 Эмуляция сети
- Профили через `tc netem` (Linux) или через два хоста / VM:
  - `lan` — 1 мс, 0% потерь (базовая линия);
  - `wifi` — 15 мс ± 5 мс джиттер, 0.5% потерь;
  - `4g` — 50 мс ± 15 мс, 1% потерь;
  - `5g` — 25 мс ± 8 мс, 0.2% потерь;
  - `lossy` — 40 мс, 5% потерь (стресс для К4/К5/К6);
  - `limited` — ограничение полосы (напр. 5 Мбит/с) для К8/стриминга.
- Профили задаются скриптом, протоколируются в результатах каждого запуска.
- **Риск (macOS):** `tc/netem` — Linux. Варианты: запуск стенда в Linux‑VM /
  Docker, либо `dummynet`/`pfctl` на macOS. Решение зафиксировать при согласовании.

### 4.2 Статистика
- Каждая точка — **N ≥ 30 повторов**; отчётные значения: среднее ± σ, медиана,
  p95, p99 (часть уже считается в `computeRttStats`).
- Прогрев (warmup) уже есть в `runRttTest` — распространить на все сценарии.
- Фиксируется окружение: версия Node, Chrome, ОС, сетевой профиль, коммит.

### 4.3 Воспроизводимость
- Автоматический прогон всех каналов × профилей через headless‑раннер
  (`scripts/e2e.mjs` как основа) с выгрузкой сырых данных в JSON/CSV.
- Результаты складываются в `results/` с меткой профиля и даты.

## 5. Перечень работ (gaps → задачи)

Пронумеровано для последующего разбиения на BMAD‑истории.

1. **Сетевые профили.** Скрипт применения/снятия профилей (`tc netem` или
   альтернатива), параметризация, логирование профиля в результат.
2. **Автоматический раннер серий.** Прогон {4 канала} × {сценарии 1–3} ×
   {N повторов} × {профили} без ручных кликов; выгрузка сырых метрик.
3. **Агрегация и статистика.** Сведение сырых данных → среднее/σ/медиана/p95/p99,
   экспорт в CSV/JSON (часть логики уже в `util.ts`).
4. **Сценарий масштабируемости (К8).** N параллельных WT‑клиентов к одному
   серверу; для WebRTC — полносвязный mesh на N участников; метрика —
   деградация RTT/потерь/CPU от N.
5. **Устойчивость к потерям (К4/К5/К6).** Прогон RTT/throughput под профилем
   `lossy` для всех 4 каналов; отдельно показать эффект HoL на надёжном канале.
6. **Накладные расходы (доп.).** Оценка служебного трафика на установление и на
   полезное сообщение (анализ на уровне счётчиков/захвата трафика).
7. **Графики и таблица результатов.** Расширить экспорт (`main.ts`, chart.js);
   итоговая таблица «критерий → измеренное значение WebRTC / WebTransport».
8. **Сопоставление с теорией.** Таблица «гипотеза H1–H6 → подтверждена/опровергнута
   → данные»; обновление `report-data.md`.
9. **Воспроизводимость/документация.** Описать hardware/soft, профили, число
   повторов; обновить README (убрать/уточнить пункты «Ограничения»).

Приоритет: **1 → 2 → 3** (без них нет валидных данных), затем 4–6 (новые
измерения), затем 7–9 (оформление).

## 7. Риски и допущения

- **Платформа эмуляции сети** (macOS vs Linux) — главный блокер Э1; решить на старте.
- **Браузер.** Сценарии 2–4 сейчас только Chrome/Chromium; Firefox/Safari — вне
  эксперимента (зафиксировать как ограничение области).
- **Сквозная задержка видео WebRTC** часто недоступна через API — измеряем
  энкодер→canvas и оговариваем это.
- Абсолютные числа зависят от стенда; акцент на **относительном** сравнении
  WebRTC vs WebTransport при одинаковых условиях.
