# WebTransport

WebTransport — второй объект сравнения. Транспорт — HTTP/3 поверх QUIC,
соединение устанавливается без сигналинга, а медиастек приложение строит само.

Реализация клиента — `src/client/transports/webtransport.ts` и
`src/client/video/wtVideo.ts`, сервера — `src/server/webtransport.ts`.

## Соединение

```ts
const wt = new WebTransport(info.wtUrl, {
  serverCertificateHashes: [{ algorithm: 'sha-256', value: hexToBytes(info.certHash).buffer }],
});
await wt.ready;
```

Адрес и отпечаток сертификата приходят из `GET /api/info`:
`wtUrl = https://<host>:<WT_PORT>/echo`, `certHash` — hex-отпечаток SHA-256
сертификата сервера. Схема `https://` обязательна: WebTransport не работает по
`http://` и в браузере доступен только в защищённом контексте (на localhost
разрешение выдаётся автоматически).

Сертификат самоподписанный: ECDSA P-256, срок 13 дней, генерируется скриптом
`scripts/gen-cert.mjs`. Если сертификата нет или до истечения осталось меньше
12 часов, он генерируется заново при старте стенда.

Измеряемое время установления соединения — это `new WebTransport()` до
`ready`, то есть криптографическое рукопожатие QUIC и установление сессии
WebTransport. Согласование ICE и обмен SDP в этом замере не участвуют.

## Каналы данных

| Канал | API | Формат |
|---|---|---|
| Надёжный поток | `createBidirectionalStream()` | кадры `[u32 длина][payload]`, `maxMessageSize = 0` |
| Дейтаграммы | `wt.datagrams.writable` | одно сообщение = одна дейтаграмма, лимит `datagrams.maxDatagramSize` (иначе 1200 байт) |

Надёжный поток — байтовый, поэтому сообщения кадрируются заголовком
`[u32 длина]`, а при приёме буфер разбирается накоплением: пока в буфере
меньше 4 + `длина` байт, кадр не выделяется. Сервер возвращает поток тем же
`pipeTo`, то есть байт-в-байт, без разбора кадров.

Дейтаграммы эхо-сервер возвращает как есть, сервер запускается с
`defaultDatagramsReadableMode: 'bytes'` — иначе `session.datagrams.readable`
не отдаёт дейтаграммы.

Обратное давление: отправка идёт через `await writer.ready` и
`await writer.write`. Для дейтаграмм это не защита от перегрузки сети — они
недоставляемы по определению.

## Видеотрансляция (сценарий 4)

```text
getUserMedia (640×480, 30 fps)
  → MediaStreamTrackProcessor
  → VideoEncoder (VP8, 1.5 Мбит/с, latencyMode: 'realtime')
  → надёжный поток QUIC
  → эхо-сервер
  → VideoDecoder (VP8)
  → <canvas>
```

Кадр на проводе (смещения считаются от начала кадра, все числа — big-endian, как
в `DataView` по умолчанию):

| Смещение | Поле | Размер |
|---|---|---|
| 0 | длина тела кадра | 4 байта |
| 4 | признак ключевого кадра | 1 байт |
| 5 | номер кадра `seq` | 4 байта |
| 9 | метка времени | 8 байт |
| 13 | данные VP8 | до конца кадра |

Поля заголовка занимают 17 байт, но константа `FRAME_HEADER` в
`src/client/video/wtVideo.ts` равна 13, поэтому данные VP8 записываются с
смещения 13 и перекрывают 4 младших байта метки времени. На кадрирование это не
влияет: длина тела и нарезка на приёме остаются согласованными, а значение
метки времени смещается на величину порядка 10⁻⁵ мс, что несопоставимо мало с
измеряемой задержкой. Побочный эффект: кадр короче 4 байт приводит к выходу
записи `f64` за границы буфера и `RangeError`, то есть на практике требуется
кадр не короче 4 байт.

Метка времени записывается в момент выхода кадра из энкодера и используется
для расчёта сквозной задержки на принимающей стороне.

Параметры кодирования и учёт нагрузки:

- `VideoEncoder`: `codec: 'vp8'`, `bitrate: 1_500_000`, `framerate: 30`,
  `latencyMode: 'realtime'`;
- ключевой кадр — каждый 60-й;
- кадр не кодируется, если `encoder.encodeQueueSize >= 3`, чтобы не копить
  очередь;
- декодер настроен на `vp8`, кадры рисуются на `canvas` по мере декодирования.

Метрики собираются раз в секунду:

| Метрика | Как считается |
|---|---|
| кадров/с | прирост числа декодированных кадров за секунду |
| скорость приёма | прирост принятых байт эха за секунду, кбит/с |
| сквозная задержка | среднее по скользящему окну из 90 последних `now − метка времени` |
| разброс задержки | сглаженное среднее отклонение `|Δe2e|` с коэффициентом `1/16` |
| RTT | не измеряется (`—`) |
| потери пакетов | не измеряются (`—`) |

Транспорт ничего не знает о медиа: кодирование, кадрирование, декодирование и
отрисовка выполняются приложением. Это обратная сторона по сравнению с WebRTC —
взамен приложение получает контроль над медиастеком, но и всю работу по нему.

## Серверная часть

```ts
const server = new Http3Server({
  port: opts.port, host: opts.host,
  cert: opts.certPem, privKey: opts.keyPem,
  defaultDatagramsReadableMode: 'bytes',
});
```

Сервер слушает UDP (`WT_PORT`, по умолчанию 4433), путь сессий — `/echo`.
Каждая сессия обслуживается двумя циклами чтения: эхо дейтаграмм и эхо
двунаправленных потоков. Сессия считается готовой после `await session.ready`;
закрытие фиксируется по `session.closed`.

Сервер запускается на `0.0.0.0`, а в `wtUrl` подставляется `127.0.0.1`, если
страницу открыли по `localhost`: Chrome может резолвить `localhost` в `::1`, а
QUIC-сервер слушает IPv4.

## Отличия от WebRTC, важные для сравнения

- Установление соединения — одно рукопожатие, без SDP и ICE.
- Дейтаграммы — родная функция QUIC, а не режим SCTP.
- Пропускная способность ограничивается flow control и backpressure
  приложения, а не поведением SCTP.
- Медиастек целиком в приложении: WebCodecs, свой кадринг, свой заголовок кадра.
- Требуется проверка сертификата через `serverCertificateHashes`, что в стенде
  решается передачей отпечатка в `/api/info`.
