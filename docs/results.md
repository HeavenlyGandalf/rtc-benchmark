# Результаты

!!! info "В репозитории нет сохранённых замеров"
    Стенд не пишет результаты в репозиторий: измерения живут в памяти вкладки
    браузера до выгрузки в CSV. Поэтому на сайте нет числовых таблиц
    измерений — есть методика, состав метрик и порядок получения данных.
    Ниже описано, что именно выдаёт стенд и как эти данные получать; значения
    нужно снимать со стенда, а не брать из документации.

## Где появляются результаты

Каждый запуск сценария добавляет строку в таблицу «Результаты» на странице
стенда. Колонки:

| Колонка | Содержимое |
|---|---|
| Сценарий | «Установление соединения», «RTT», «Пропускная способность» |
| Транспорт | подпись канала из `MODE_LABELS` |
| Параметры | размер, число сообщений или длительность, интервал — **запрошенные** значения, без учёта автоматического уменьшения размера под лимит канала |
| Метрики | набор «ключ: значение», пары разделены `; ` |

## Состав метрик

| Сценарий | Метрики в строке результатов |
|---|---|
| 1 — установление соединения | среднее, мс; медиана, мс |
| 2 — RTT | среднее, мс; медиана, мс; p95, мс; p99, мс; разброс задержки (RFC 3550), мс; σ, мс; потери, % |
| 3 — пропускная способность | Мбит/с; отправлено сообщ.; получено сообщ.; потери, % |
| 4 — видео | выводятся раз в секунду в блоке статистики под кнопкой: сквозная задержка, кадров/с, скорость приёма, разброс задержки, RTT, потери пакетов |

Видеометрики — потоковые, они не попадают в таблицу результатов: их нужно
записывать вручную или снимать с экрана (автоматический e2e-прогон печатает их
в консоль и сохраняет скриншот).

## Выгрузка в CSV

Кнопка «Экспорт CSV» внизу страницы выгружает все накопленные строки:

- разделитель — `;`, чтобы файл открывался в Excel и LibreOffice без
  настройки импорта;
- в начало файла добавляется BOM для корректного определения UTF-8;
- первая строка — заголовки: `Сценарий;Транспорт;Параметры;` и далее все
  ключи метрик, встреченные в результатах;
- имя файла — `rtc-benchmark-<метка времени>.csv`.

## Как получить данные для сравнения

1. Запустить стенд и убедиться, что в шапке страницы
   `✓ Все необходимые API поддерживаются (Chromium)`.
2. Выполнить сценарии 1–3 с одинаковыми параметрами для всех каналов — каждый
   сценарий сам проходит все четыре канала, поэтому параметры достаточно задать
   один раз.
3. Повторить прогон несколько раз: на loopback разброс времени установления
   соединения заметен, поэтому единичный замер не показателен.
4. Выгрузить CSV и сопоставить строки по колонкам «Сценарий» и «Транспорт».
5. Отдельно снять видеометрики (блок статистики под кнопками сценария 4) или
   воспользоваться автоматическим прогоном.

## Автоматический прогон e2e

`yarn e2e` открывает стенд в headless Chrome с фейковой камерой, прогоняет все
четыре сценария с уменьшенными параметрами (3 повтора установления соединения,
50 сообщений RTT, 2 секунды на пропускную способность), печатает таблицу
результатов в консоль и сохраняет скриншот в `results/e2e-screenshot.png`.

Пример такого вывода приведён в `README.md` как иллюстрация формата консоли.
Это разовый прогон на конкретной машине, а не результаты исследования: его
нельзя использовать как справочные данные.

## Время публикации самого сайта

Отдельно от метрик стенда измеряется публикация документации: насколько долго
workflow выкладывает сайт. Эти числа не зависят от стенда, их удобно снимать
из API GitHub по конкретным запускам workflow.

| Задание | Старая схема, среднее | Новая схема, среднее |
|---|---|---|
| Публикация на Helios | 72,0 с | 28,0 с |
| Публикация на GitHub Pages | 12,3 с | 11,4 с |
| Проверка опубликованного сайта (только новая) | — | 3,4 с |

![Столбиковая диаграмма: публикация на Helios сократилась с 72 до 28 секунд, публикация на GitHub Pages почти не изменилась — с 12,3 до 11,4 секунд, и к ней добавилась проверка опубликованного сайта, из-за чего вместе они занимают 14,8 секунды](assets/images/publish-time.svg)

Разница объясняется тем, что делает публикация. На Helios старая схема
выкладывала все файлы целиком в рабочий каталог, новая — `rsync` в отдельный
каталог релиза и переносит только изменившиеся файлы. На Pages схема
изменилась меньше: там публикация идёт через `deploy-pages`, и добавилась
только проверка опубликованного сайта — она и даёт эти лишние 3,4 секунды.

Методика замера и сами запуски перечислены в [Отчёте об отладке](debugging.md).

## Как читать результаты

- **Время установления соединения.** Сравнивать среднее и медиану: медиана
  устойчива к выбросам, которые на loopback дают отдельные медленные повторы.
- **RTT.** Основной показатель — медиана и p95/p99; σ и джиттер показывают
  разброс. У ненадёжных каналов обязательно смотрите на потери: они могут
  объяснять «пропуски» в графике.
- **Пропускная способность.** Размер сообщения в колонке «Параметры» —
  запрошенный, а не фактический: у ненадёжных каналов он уменьшается до лимита
  канала, см. [Ограничения размера сообщения](methodology.md#message-size).
  Сравнивайте строки, заведомо отправлявшие одинаковый объём данных.
- **Видео.** Сквозная задержка WebRTC обычно недоступна, поэтому для сравнения
  задержки используйте видеосценарий WebTransport и помните, что она не
  включает задержку вывода на экран.
- **Абсолютные значения.** На loopback единицы миллисекунд и десятки мегабит в
  секунду — это предел измерений на одной машине, а не характеристики
  транспортов в сети. Сравнивать нужно относительные различия при одинаковых
  условиях, а не сами числа. Подробнее — [Ограничения](limitations.md).
