# rtc-benchmark

Экспериментальный стенд к НИР «Сравнительный анализ технологий WebRTC и WebTransport
для передачи данных в реальном времени в веб-приложениях».

Стенд измеряет WebRTC и WebTransport на одинаковых сценариях: время установления
соединения, задержку обмена и её разброс, пропускную способность и видеотрансляцию
через сервер (камера → транспорт → эхо-сервер → экран).

---

## 1. Требования

| Что | Версия / примечание |
|---|---|
| Node.js | **20 или новее** (проверено на 20.20.2), с поддержкой `fetch` |
| Yarn | **4.18.0** — подтягивается автоматически через Corepack (`packageManager` в `package.json`) |
| Браузер | **Chrome / Chromium** для сценария 4 и WebTransport в целом |
| openssl | нужен для генерации сертификата (есть в macOS и Linux из коробки) |
| Камера | для видеосценария нужен либо реальный девайс, либо фейковая камера Chrome |

Проверено на macOS (darwin/arm64). На Windows генерация сертификата требует
установленного `openssl` в PATH.

---

## 2. Быстрый старт

```bash
corepack enable          # один раз: активировать Yarn 4 из package.json
yarn install             # установка зависимостей + нативного модуля QUIC
yarn start               # сборка клиента и запуск стенда
```

Откройте **http://localhost:8080** — в шапке должно быть
`✓ Все необходимые API поддерживаются (Chromium)`.

`yarn start` делает три things:

1. собирает клиентский бандл `public/app.js` из `src/client/**` (esbuild);
2. генерирует самоподписанный сертификат для WebTransport, если его нет или
   осталось меньше 12 часов;
3. поднимает два слушателя сервера.

Ожидаемый вывод:

```
⚡ Done in 85ms
[CERT] генерирую новый ECDSA-сертификат (срок 13 дней)...
Сертификат создан: .../certs/cert.pem
sha256 Fingerprint=D0:2F:C3:...
[WT]   WebTransport (HTTP/3) слушает udp://0.0.0.0:4433, путь /echo
[HTTP] стенд доступен:    http://localhost:8080
[CERT] sha-256 отпечаток: D02FC36D...
```

Остановить стенд — `Ctrl+C` в терминале.

> Камеру и микрофон браузер спросит при нажатии кнопок видеосценария — на localhost
> разрешение выдаётся автоматически.

## 3. Команды

| Команда | Что делает |
|---|---|
| `yarn install` | Установка зависимостей. Собирает нативный модуль QUIC при первом запуске (1–2 минуты) |
| `yarn start` | Сборка клиента + запуск стенда (основная команда) |
| `yarn dev` | То же самое, но сервер перезапускается автоматически при правках в `src/server` |
| `yarn build` | Только сборка клиента: `src/client/main.ts` → `public/app.js` + sourcemap |
| `yarn typecheck` | Проверка типов всего `src/**` (tsc, без emit) |
| `yarn cert` | Принудительная перегенерация сертификата |
| `yarn test` | Smoke-тесты эха: WebRTC DataChannel, затем WebTransport (поток + дейтаграмма) |
| `yarn test:rtc` | Только WebRTC-часть |
| `yarn test:wt` | Только WebTransport-часть |
| `yarn e2e` | Полный прогон стенда в headless Chrome, делает скриншот |

> **Важно:** после ручной правки файлов в `src/client/**` нужно выполнить `yarn build`
> (или запустить стенд через `yarn start` / `yarn dev`, они пересобирают бандл сами).
> Файл `public/app.js` лежит в репозитории и используется сервером как есть.

## 5. Как пользоваться стендом

Все сценарии на странице можно запускать по одному, каждый считает по всем
четырём каналам (надёжный поток и дейтаграммы WebTransport, надёжный и ненадёжный
каналы данных WebRTC) и сравнивает их между собой.

**Сценарий 1 — время установления соединения.** Задайте число повторов и нажмите
«Запустить». Для WebTransport измеряется `new WebTransport()` → `ready`; для WebRTC —
полный цикл: SDP-предложение → сбор кандидатов ICE → HTTP-сигналинг → DTLS →
открытие канала данных. В таблице появятся среднее и медиана для каждого транспорта.

**Сценарий 2 — задержка обмена (RTT), её разброс и потери.** Классический поочерёдный
обмен: отправляете сообщение, сервер возвращает его как есть, замеряется время
туда-обратно. Столбцы — размер сообщения и интервал отправки. Строится график по
сообщениям + сводка (среднее/медиана/p95/p99/разброс задержки/σ/потери). Учтите: у
ненадёжных каналов размер одного сообщения ограничен (~1200 Б для дейтаграмм,
`sctp.maxMessageSize` для каналов данных) — при вводе большего значения он
автоматически уменьшается, о чём стоит помнить при сравнении.

**Сценарий 3 — пропускная способность.** Отправка непрерывного потока сообщений
заданного размера в течение N секунд с учётом обратного давления. Считается
**скорость приёма эха** — сколько байт реально вернулось от сервера; поэтому
результат отражает и клиент, и сервер, и канал. Для ненадёжных каналов фиксируются
потери.

**Сценарий 4 — видеотрансляция (передача через сервер).** Две кнопки, каждая
запускает свою цепочку:

- **WebRTC** — `getUserMedia` → `RTCPeerConnection` (встроенная медиасреда:
  согласование кодека через SDP, SRTP, подстройка скорости передачи) → сервер
  возвращает RTP-пакеты обратно → `<video>`. Статистика из `getStats()`: сквозная
  задержка, кадров/с, скорость приёма, разброс задержки, RTT, потери пакетов.
- **WebTransport** — `MediaStreamTrackProcessor` → `VideoEncoder` (VP8, 1.5 Мбит/с)
  → надёжный поток QUIC → эхо-сервер → `VideoDecoder` → `<canvas>`. Медиасреда
  полностью в приложении: транспорт о медиа ничего не знает.

**Экспорт CSV** — кнопка внизу страницы выгружает все накопленные результаты
(разделитель `;`, BOM для корректного открытия в Excel).

## 6. Тесты

### Smoke-тесты эха

```bash
# в одном терминале — стенд
yarn start

# в другом — тесты
yarn test
```

Ожидаемый вывод:

```
OK: data channel открыт
OK: эхо DataChannel: ping-123
OK: сессия установлена
OK: эхо потока: 000000050102030405
OK: эхо дейтаграммы: 090909
```

Тесты подключаются к стенду как обычные клиенты, но из Node, поэтому дополнительно
проверяют, что эхо-сервер работает на обоих транспортах.

### E2E-тест в браузере

```bash
yarn start     # терминал 1
yarn e2e       # терминал 2
```

Тест открывает стенд в headless Chrome с фейковой камерой, прогоняет все четыре
сценария с уменьшенными параметрами (3 повтора установления, 50 сообщений RTT,
2 секунды на throughput), печатает таблицу результатов и сохраняет скриншот в
`results/e2e-screenshot.png`. Камера эмулируется флагами
`--use-fake-device-for-media-stream`, отдельная установка не нужна.

Пример вывода:

```
Поддержка API: ✓ Все необходимые API поддерживаются (Chromium)
Сценарий 1 WT:  среднее 3.00 мс, медиана 2.40 мс
Сценарий 1 RTC: среднее 204.17 мс, медиана 131.60 мс
...
=== Таблица результатов ===
Пропускная способность | WebTransport / надёжный поток | 2 с, сообщения по 16384 Б | Мбит/с: 317.69; ...
```

Если браузер установлен нестандартно:

```bash
CHROME_PATH=/path/to/chrome yarn e2e
```

## 7. Устройство проекта

```
src/
  client/
    main.ts               UI: запуск сценариев, графики (chart.js), экспорт CSV
    bench.ts              три сценария; единый интерфейс BenchChannel
    util.ts               формат измеренных сообщений и статистика
    transports/
      types.ts            BenchChannel — общий интерфейс всех каналов
      webtransport.ts     WT-поток (кадрирование [u32 len][payload]) и WT-дейтаграммы
      webrtc.ts           DataChannel надёжный/ненадёжный, сигналинг через HTTP
    video/
      webrtcVideo.ts      видео через встроенный медиастек WebRTC
      wtVideo.ts          видео через WebCodecs (VP8) поверх QUIC-потока
  server/
    index.ts              HTTP-1.1 сервер: статика, /api/info, /api/webrtc/offer; запуск WT-сервера
    webrtc.ts             echo-сервер на node-datachannel (DataChannel + RTP)
    webtransport.ts       echo-сервер на HTTP/3 (потоки + дейтаграммы)
public/                   статика: index.html, styles.css, app.js (собранный бандл)
scripts/                  gen-cert.mjs, smoke-тесты, e2e.mjs
certs/                    самоподписанный сертификат (генерируется автоматически)
results/                  скриншоты и выгрузки e2e
docs/                     исходники сайта документации (MkDocs Material)
mkdocs.yml                конфигурация сайта документации
.github/workflows/        автоматическая сборка и публикация сайта
LICENSE                   MIT — на код
LICENSE-CONTENT.md        CC BY 4.0 — на материалы сайта
```

### Потоки данных

| Сценарий | Клиент → сервер | Сервер → клиент |
|---|---|---|
| WT надёжный поток | `createBidirectionalStream()`, кадры `[u32 len][payload]` | `pipeTo` того же потока (байт-в-байт) |
| WT дейтаграммы | `wt.datagrams.writable` | эхо входящей дейтаграммы |
| DataChannel надёжный | `createDataChannel('reliable')` | эхо сообщения |
| DataChannel ненадёжный | `createDataChannel('unreliable', {ordered:false, maxRetransmits:0})` | эхо сообщения |
| Видео WebRTC | `addTrack` → RTP по SRTP | те же RTP-пакеты обратно |
| Видео WebTransport | `VideoEncoder` → QUIC-поток, кадр `[u32 len][u8 key][u32 seq][f64 ts][VP8]` | байт-в-байт эхо → `VideoDecoder` |

Сигналинг — единственный неэхо-обмен: браузер отправляет `POST /api/webrtc/offer`
с SDP, сервер отвечает SDP-ответом после полного сбора ICE-кандидатов
(trickle ICE не используется, латентность установления поэтому включает
ожидание кандидатов). Хеш сертификата для WebTransport клиент получает из `GET /api/info`.

Измеряемые сообщения имеют заголовок `[uint32 seq][float64 sendTime][padding]`,
эхо-сервер работает со всеми каналами одинаково — это и обеспечивает сопоставимость
метрик.

### Конфигурация

- `.yarnrc.yml` — `packageExtensions` объявляет нативный транспорт
  `@fails-components/webtransport-transport-http3-quiche`, который библиотека
  подгружает динамически и не указывает в своих зависимостях (без этого PnP
  блокирует загрузку QUIC-модуля).
- `tsconfig.json` — единая конфигурация для клиента и сервера: `strict`,
  `moduleResolution: Bundler`, `customConditions: ["node"]` (нужно, чтобы
  TypeScript видел node-условие в `exports` у WebTransport-пакета).
- `package.json` → `dependenciesMeta` разрешает install-скрипт нативного QUIC-модуля
  (Yarn 4 по умолчанию не запускает build-скрипты).

## 8. Известные ограничения

1. **Только Chromium.** WebTransport, WebCodecs и `MediaStreamTrackProcessor`
   поддерживаются в Chrome/Edge; в Firefox и Safari сценарии 2–4 работать не будут
   (проверка выводит предупреждение в шапке страницы).
2. **Измерения только на loopback.** Клиент и сервер — один и тот же хост, реальная
   сеть, MTU и задержка не моделируются. Абсолютные цифры RTT (доли миллисекунды)
   и скорости (десятки Мбит/с) — это предел loopback, а не характеристики
   транспортов в сети. Для выводов о преимуществах нужен `tc/netem` или несколько машин.
3. **Сервер — один поток Node.** Он одновременно обслуживает сигналинг, эхо
   DataChannel и эхо RTP; при работающем видео нагрузка конкурирует с бенчмарком
   данных, поэтому видеосценарий и сценарии 1–3 не стоит запускать одновременно.
4. **Метрика «сквозная задержка» для WebRTC обычно недоступна** (в таблице будет `—`):
   временные метки захвата камеры не переносятся через WebRTC-стек, и
   `VideoFrameCallbackMetadata.captureTime` приходит пустым. Для WebTransport
   эта метрика считается, но от момента выхода кадра из энкодера до отрисовки
   на canvas, то есть без учёта задержки вывода на экран.
5. **Доля потерь в сценарии 3** зависит от фиксированного 700 мс ожидания дренажа
   очередей: для надёжных каналов при большом объёме хвост может не вернуться
   и попасть в «потери».
6. **Сертификат живёт 13 дней** и самоподписанный: Chrome принимает его только
   через `serverCertificateHashes` и только для ключа ECDSA P-256, поэтому
   `gen-cert.mjs` жёстко использует `-newkey ec -pkeyopt ec_paramgen_curve:prime256v1`
   и `-days 13`. При истечении сертификат перегенерируется при следующем старте.
7. **Замеры не покрывают сеть с потерями**: нет TURN (`iceServers: []`),
   нет эмуляции задержки, её разброса и перегрузки.

## 9. Если что-то не запускается

| Симптом | Причина и решение |
|---|---|
| `Error: This package doesn't seem to be present in your lockfile` | Не установлены зависимости или удалён `yarn.lock`: выполните `yarn install` |
| `Cannot find module ...` при запуске | Не выполнен `yarn install`. Стирать `.pnp.cjs` вручную не нужно — его пересоздаёт установка |
| `Problem loading http3-quiche transport` | Не собран нативный модуль QUIC: `yarn install` (или `yarn rebuild @fails-components/webtransport-transport-http3-quiche`) |
| `Top-level await is currently not supported with the "cjs" output format` | В `package.json` потерян `"type": "module"` — без него tsx считает `.ts` CommonJS |
| `yarn tsc` не находит файлы | В `tsconfig.json` должен быть `"include": ["src/**/*.ts"]`, а не несуществующий каталог |
| Порт 8080 или 4433 занят | `HTTP_PORT=8081 WT_PORT=4434 yarn start` либо освободите порт |
| `EADDRINUSE: udp 4433` | Занят QUIC-порт, аналогично: смените `WT_PORT` |
| `Стeнд не отвечает` при `yarn e2e` | Стенд не запущен: откройте `yarn start` в другом терминале |
| `Failed to launch the browser process` в e2e | Chrome не найден: укажите `CHROME_PATH=/путь/к/chrome` |
| WebTransport не подключается, а HTTP работает | Проверьте, что UDP-порт 4433 не заблокирован файрволом; попробуйте другой `WT_PORT` |
| В шапке страницы список unsupported API | Открыли не в Chromium либо браузер блокирует камеру вне HTTPS/localhost |
| `Chrome: invalid certificate` | Удалите `certs/`, затем `yarn cert` — сертификат пересоздастся |
| Метрики suspiciously быстрые, RTT < 1 мс | Это нормально для loopback: смотрите раздел 8, пункт 2 |

## 10. Безопасность

Стенд предназначен для локального запуска и не содержит авторизации: эхо-сервер
принимает соединения от любого клиента и возвращает то, что прислали. При запуске
на общей сети имейте в виду, что порты 8080 (HTTP) и 4433 (UDP) будут видны в
локальной сети. Для стенда на одной машине это не имеет значения.

## 11. Сайт документации

Отдельный статический сайт с описанием методики, архитектуры стенда, сценариев,
ограничений, отчёта об отладке и лицензий собирается на
[MkDocs Material](https://squidfunk.github.io/mkdocs-material/). Стенд при этом
не меняется: сайт только читает его код и README.

```bash
python3 -m venv .venv-docs                 # один раз: окружение для сайта
.venv-docs/bin/pip install -r requirements.txt

.venv-docs/bin/mkdocs serve                # предпросмотр на http://localhost:8000
.venv-docs/bin/mkdocs build --strict       # строгая сборка в каталог site/
```

Исходники страниц — в `docs/`, конфигурация — в `mkdocs.yml`, версии
зависимостей зафиксированы в `requirements.txt`. Каталог сборки `site/` и
окружение `.venv-docs/` в репозиторий не попадают.

> На macOS бинарник Python — `pip3`, а не `pip`. Отдельная установка
> `virtualenv` не нужна: `python3 -m venv` достаточно, поскольку состав
> зависимостей полностью зафиксирован в `requirements.txt`.

### Публикация

Сайт публикуется автоматически: при каждом пуше в `main` workflow
`.github/workflows/deploy.yml` собирает сайт и выкладывает его в GitHub Pages
официальной связкой `upload-pages-artifact` + `deploy-pages`.

Разовая обязательная настройка в репозитории:
**Settings → Pages → Source = GitHub Actions**.

Адрес публикации задаётся единственным полем `site_url` в `mkdocs.yml`; при его
смене правится только эта строка. Отдельного `base_url` в MkDocs 1.6 не
существует. Подробности — на странице «Как запустить стенд» и в отчёте об
отладке.
